# Feature Specification: Orders Oversight

**Feature Branch**: `007-orders-oversight`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "Phase 7 — Orders Oversight (from admin-dashboard-api.md). Goal: a read-only monitoring screen inside the admin dashboard that lets an administrator see every order on the platform, with filters (status, city, placed-date range) and pagination. All access is under /admin and requires an administrator session; a signed-in user whose role is not admin is denied. GET /admin/orders returns a paginated list — { items, page, per_page, total } with per_page fixed at 20 and navigation via ?page=N. Query params: status (one of the OrderStatus values: pending, accepted, preparing, ready_for_pickup, assigned_to_driver, picked_up, on_the_way, delivered, completed, cancelled, pending_review, quoted), city_id (the cook's city; a city that exists but is deactivated is still accepted, a city_id that does not exist gives 422), placed_from and placed_to (a date Y-m-d or ISO; placed_to is snapped to 23:59:59), page (default 1). Each order item carries id, order_number, customer_id, cook_id, cook_name, cook_avatar_url, type (regular | custom), status, delivery_address_id, requested_delivery_date, delivery_time_slot, subtotal, delivery_fee, total, customer_note, cancel_reason, items[] (id, dish_id, item_name, unit_price, quantity, line_total), custom_details (null for regular; for custom it holds occasion_type, guest_count, requested_dishes_text, budget_min, budget_max, requested_delivery_date_time), quote (always null in list results) and status_history (always [] in list results). Errors: 422 for an invalid status value, a non-existent city_id, an invalid date, or placed_from later than placed_to. Standard success/error envelope { success, data, message, errors }; status codes 401 unauthenticated, 403 non-admin, 422 validation / domain-rule violation, 500 unexpected. UI: an Orders Oversight page inside the dashboard with a paginated table of orders, filters for status, city, and placed-date range, a way to inspect a single order's line items and (for custom orders) its custom details, clear display of API validation errors (especially the invalid-date and placed_from-after-placed_to cases), loading / empty / error states, and an Arabic RTL-first layout."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Administrator reviews the platform's orders (Priority: P1)

An administrator opens the Orders Oversight area of the dashboard and sees a table of orders placed across the platform, one page at a time. Each row shows enough to identify and triage the order at a glance: its order number, the cook it belongs to, whether it is a regular or a custom order, its current status, the date and time slot the customer asked for delivery, and the money involved (items subtotal, delivery fee, and total). The list is paged in fixed-size pages, and the administrator can move between pages and see how many orders match in total. Loading, empty, and error states are all explicit.

**Why this priority**: The whole point of the phase is letting an administrator observe order activity on the platform. With only this story implemented — a paginated, readable list of orders with their status and totals — an administrator can already monitor what is happening, which is the minimum useful slice. Every other story narrows or drills into this list.

**Independent Test**: Sign in as an administrator, open the Orders Oversight area, and confirm that a page of orders placed in the last 30 days is shown with order number, cook, type, status, requested delivery date and time slot, subtotal, delivery fee, and total; that the default "last 30 days" range is shown pre-set and can be widened or cleared; that a loading state shows while the page is being retrieved; that an explicit empty state shows when no orders match; that the total count (labelled as within the applied range) and current page are shown; and that moving to the next and previous pages retrieves and shows the corresponding orders.

**Acceptance Scenarios**:

1. **Given** the platform has more orders in the last 30 days than fit on one page, **When** the administrator opens the Orders Oversight area, **Then** a default placed-date range of the last 30 days is applied and shown pre-set in the filters, and the first page of matching orders is shown in a table, each row showing at least the order number, cook name, order type (regular or custom), status, requested delivery date and time slot, subtotal, delivery fee, and total, together with the current page number and the total number of orders within the applied range.
1a. **Given** the default "last 30 days" range is in effect, **When** the administrator widens or clears it, **Then** the list re-runs from the first page for the new range and the total count reflects it.
2. **Given** the order list is being retrieved, **When** the data has not yet arrived, **Then** a loading state is shown that is distinct from the empty state.
3. **Given** no orders match the current view, **When** the area is shown, **Then** an explicit "no orders" state is shown rather than a blank table.
4. **Given** the administrator is on the first page and more pages exist, **When** they move to the next page, **Then** the next set of orders is retrieved and shown, the page indicator updates, and the "previous page" control becomes available.
5. **Given** the administrator is on a later page, **When** they move to the previous page or back to the first page, **Then** the corresponding orders are retrieved and shown.
6. **Given** an order in the list is a custom order, **When** the row is shown, **Then** it is clearly marked as a custom order and distinguishable from a regular order without relying on colour alone.
7. **Given** an order in the list has been cancelled, **When** the row is shown, **Then** its status is clearly shown as cancelled, and where a cancellation reason is present it is available to the administrator (in the row or the order's detail).
8. **Given** the list request fails due to connectivity or an unexpected server error, **When** the failure occurs, **Then** the administrator sees a retryable "something went wrong, please try again" message and is not shown a blank list presented as authoritative.
9. **Given** the administrator requests a page number beyond the last page of results, **When** the response contains no items, **Then** the area shows an explicit "no orders on this page" state and offers a way back to the first page rather than appearing broken.

### User Story 2 - Administrator filters orders by status, city, and date placed (Priority: P2)

The administrator narrows the list to the orders they care about: only orders in a particular status (for example only `pending_review` or only `cancelled`), only orders belonging to cooks in a particular city, and/or only orders placed within a date range. Filters combine, the result is still paged, and the total count reflects the filtered set. Invalid filter input — an unknown status, a city that does not exist, a malformed date, or a start date later than the end date — is reported clearly and the list is not left in a misleading state.

**Why this priority**: A flat list of every order on the platform is hard to act on at scale. Filtering by status, city, and date is what turns the oversight screen into a working tool — for example finding all orders awaiting review, or all cancellations in one city last week. It builds directly on Story 1.

**Independent Test**: With the list on screen, apply a status filter and confirm only orders in that status are shown and the total updates; apply a city filter and confirm only orders for that city's cooks are shown, including when the chosen city is deactivated; apply a placed-from / placed-to range and confirm only orders placed in that window are shown, with the end date treated as inclusive of the whole day; set placed-from later than placed-to and confirm the administrator is told the range is invalid and no misleading results are shown; clear the filters and confirm the full list returns.

**Acceptance Scenarios**:

1. **Given** the list is on screen, **When** the administrator selects a single status, **Then** the filter applies immediately, only orders in that status are shown, the total count reflects the filtered set, and pagination restarts from the first page of the filtered results.
2. **Given** a status filter is applied, **When** the administrator clears it, **Then** the list returns to all statuses.
3. **Given** the list is on screen, **When** the administrator selects a city and applies it, **Then** only orders whose cook is in that city are shown.
4. **Given** the administrator opens the city filter, **When** they choose a city that is currently deactivated but still exists, **Then** the filter is accepted and the matching orders are shown (a deactivated city is a valid filter value).
5. **Given** the list is on screen, **When** the administrator sets a placed-from date and a placed-to date and applies them, **Then** only orders placed on or after the start of the from-date and on or before the end (23:59:59) of the to-date are shown.
6. **Given** the administrator sets only a placed-from date or only a placed-to date, **When** they apply it, **Then** the range is treated as open-ended on the unset side and the matching orders are shown.
7. **Given** the administrator sets a placed-from date later than the placed-to date, **When** they use the "Apply" control, **Then** no request is sent, they are shown a clear "the start date must not be after the end date" message against the date fields, and the previously shown results are unchanged.
8. **Given** the administrator enters or selects a date that the platform rejects as invalid, **When** the filter is applied, **Then** a clear invalid-date message is shown and no filtered request is treated as successful.
9. **Given** the platform reports an unknown or unsupported status value, **When** the filter is applied, **Then** a clear message is shown and the list is not updated with results for an invalid filter. (The status control should only offer supported values, so this is a safeguard.)
10. **Given** the platform reports that the chosen city does not exist, **When** the filter is applied, **Then** a clear "city not found" message is shown and the list is not updated. (The city control should only offer real cities, so this is a safeguard.)
11. **Given** several filters are applied together, **When** the administrator changes one of them, **Then** the others remain in effect and the combined filter is re-applied from the first page.
12. **Given** filters that match no orders, **When** they are applied, **Then** an explicit "no orders match these filters" state is shown, distinct from the unfiltered "no orders" state, with the filters still visible and adjustable.
13. **Given** filters are applied and the administrator moves between pages, **When** each page is retrieved, **Then** the same filters stay in effect for every page.

### User Story 3 - Administrator inspects a single order in detail (Priority: P3)

From a row in the list, the administrator opens the full detail of one order: every line item with its dish name, unit price, quantity, and line total; the order's subtotal, delivery fee, and total; the customer's note; the cancellation reason if it was cancelled; and, for a custom order, its custom details — the occasion, the guest count, the free-text description of the dishes requested, the budget range, and the requested delivery date and time.

**Why this priority**: The list row is a summary; understanding why an order looks the way it does — what was ordered, what a custom request asked for, why it was cancelled — needs the line-item and custom-detail breakdown. It builds on Story 1 and is the deepest level of the oversight screen.

**Independent Test**: Open the detail for a regular order and confirm every line item is shown with dish name, unit price, quantity, and line total, that the line totals are consistent with the order subtotal, and that the customer note is shown when present; open the detail for a custom order and confirm the custom details block (occasion, guest count, requested-dishes text, budget range, requested delivery date/time) is shown; open the detail for a cancelled order and confirm the cancellation reason is shown.

**Acceptance Scenarios**:

1. **Given** an order in the list, **When** the administrator opens its detail, **Then** they see the order number, the cook, the order type, the status, the requested delivery date and time slot, the subtotal, delivery fee, and total, and the customer identifier and delivery-address identifier shown as labelled reference numbers (no customer name or textual address).
2. **Given** the order has line items, **When** the detail is shown, **Then** every line item is listed with its item name, unit price, quantity, and line total.
3. **Given** the order has a customer note, **When** the detail is shown, **Then** the note is shown; **and given** it has none, **then** the note area is absent or shown as empty rather than showing a placeholder as if it were content.
4. **Given** the order was cancelled with a reason, **When** the detail is shown, **Then** the cancellation reason is shown; **and given** it was not cancelled, **then** no cancellation reason is shown.
5. **Given** the order is a custom order, **When** the detail is shown, **Then** the custom details are shown — the occasion type, the guest count, the requested-dishes text, the minimum and maximum budget, and the requested delivery date and time.
6. **Given** the order is a regular order, **When** the detail is shown, **Then** no custom-details block is shown.
7. **Given** the administrator is viewing an order's detail, **When** they close it, **Then** they are returned to the same page and position in the list they came from, with any filters still in effect.
8. **Given** an order's status history and any price quote are not available on this screen, **When** the detail is shown, **Then** the screen does not present an empty timeline or an empty quote as if data were missing — those sections are simply not rendered in this phase, though the layout keeps a defined place for them to be added later.
9. **Given** the detail is built only from data already in the list response, **When** the administrator opens it, **Then** no additional per-order request is made.

### Edge Cases

- **Unknown status filter value**: the platform rejects a status it does not recognise with a validation error — the administrator sees a clear message and the list is not updated for the invalid filter; the status control only offers the supported values so this should not arise in normal use.
- **Non-existent city filter value**: the platform rejects a `city_id` that does not exist with a validation error — the administrator sees a "city not found" message and the list is not updated; the city control only offers real cities so this is a safeguard.
- **Deactivated city as a filter**: a city that exists but is switched off is a valid filter value — orders for that city's cooks are still shown.
- **Invalid date input**: a date the platform cannot parse is rejected with a validation error — the administrator sees a clear invalid-date message and no filtered request is treated as successful.
- **Start date after end date**: `placed_from` later than `placed_to` is rejected — the administrator is told the start date must not be after the end date, and the previously shown results are not replaced by misleading ones.
- **End date treated as inclusive**: the to-date covers the whole day up to 23:59:59, so an order placed late on the to-date is still included.
- **Open-ended range**: only a from-date or only a to-date is allowed; the unset side is treated as unbounded.
- **Page beyond the last page**: a requested page past the end of the results returns no items — an explicit "no orders on this page" state is shown with a way back to the first page, not a broken-looking screen.
- **Filter change resets paging**: applying or changing any filter returns the view to the first page of the new result set so the page indicator and results always agree.
- **Custom order with missing optional custom fields**: a custom order whose custom details omit some values shows only the values present, without placeholders implying data is missing.
- **Order with no line items**: a custom order may have an empty `items` list before it is quoted — the detail shows the custom details and an explicit "no line items yet" rather than an empty table with no explanation.
- **Very large totals or long free-text**: large money values and long customer notes or requested-dishes text are shown without breaking the table or detail layout.
- **Quote and status history absent**: `quote` is always empty and `status_history` is always empty on this screen — the detail does not show an empty quote or an empty timeline as if data failed to load.
- **Empty result for a valid filter**: valid filters that simply match nothing show a "no orders match these filters" state distinct from the unfiltered empty state, with the filters still adjustable.
- **Session lost mid-task**: a list request is rejected as unauthenticated — handled by the dashboard's shared session-loss behaviour (return to sign-in), consistent with the authentication feature; the administrator is not shown a broken view.
- **Non-administrator reaches the area**: access is refused; this area is only reachable within an administrator session, and a signed-in user whose role is not administrator is denied.
- **Unexpected server error on any request**: the administrator sees a generic "something went wrong, please try again" message and a way to retry, with no stale page shown as authoritative.
- **Concurrent changes to an order**: an order's status may change on the platform between when a page is retrieved and when the administrator reads it — this is a read-only screen, so the next retrieval simply shows the current state; nothing is locked or held.
- **Default date window on open**: opening the area applies a "last 30 days" placed-date range; an order placed 31 days ago is not shown until the administrator widens or clears the range. The total count reflects this range, not the platform total.
- **Auto-refresh scope**: automatic re-retrieval runs only on the first results page with the default (or wider) date range and no custom narrower range; moving to page 2, narrowing the date range, or turning it off stops it. An automatic refresh never moves the administrator's scroll position, changes the applied filters, or closes an open order detail.
- **Auto-refresh while reading a detail**: if an automatic refresh occurs while an order's detail is open, the detail stays open and unchanged; the underlying list updates behind it and reconciles when the detail is closed.
- **Future timeline/quote placeholder**: the detail layout reserves a place for a status timeline and price quote to be added in a later phase; in this phase that place renders nothing at all (not an empty or "loading" section).

## Requirements *(mandatory)*

### Functional Requirements

#### Viewing the order list

- **FR-001**: The dashboard MUST provide an Orders Oversight area, reachable only within an administrator session, that lists orders placed across the platform in fixed-size pages of 20, with navigation between pages by page number.
- **FR-002**: For each order in the list, the dashboard MUST display at least the order number, the cook (name, and avatar where provided), the order type (regular or custom), the current status, the requested delivery date and time slot, and the order's subtotal, delivery fee, and total. The list MUST NOT include a customer column (only a numeric `customer_id` is available and it is shown in the detail only).
- **FR-003**: The dashboard MUST show the current page number and the total number of matching orders, and MUST provide controls to move to the next page, the previous page, and back to the first page, disabling each control when it does not apply.
- **FR-004**: The dashboard MUST make custom orders visually distinguishable from regular orders, and cancelled orders clearly identifiable, by more than colour alone (for example a text label or icon).
- **FR-005**: The dashboard MUST show a loading state while a page of orders is being retrieved, distinct from the empty state.
- **FR-006**: When no orders match the current view, the dashboard MUST show an explicit empty-state message rather than a blank table.
- **FR-007**: When a requested page is beyond the last page of results (no items returned), the dashboard MUST show an explicit "no orders on this page" state and offer a way back to the first page.
- **FR-008**: If a list request fails due to connectivity or an unexpected server error, the dashboard MUST show a retryable "something went wrong, please try again" message and MUST NOT present a blank or stale list as authoritative.
- **FR-009**: The dashboard MUST let the administrator refresh the current view on demand, re-retrieving the current page with the current filters.
- **FR-009a**: The dashboard MUST automatically re-retrieve the current view on a recurring interval, but ONLY while the first page of results is shown AND the administrator has not narrowed the placed-date range below the default window (i.e. the default "last 30 days" range or a wider one is in effect). On any later page, or when the administrator has set a custom (narrower) date range, auto-refresh MUST be off and refresh is manual only.
- **FR-009b**: The administrator MUST be able to turn auto-refresh off. An automatic refresh MUST NOT move the administrator's scroll position or selection, MUST NOT reset the applied filters, and MUST NOT close an open order detail.
- **FR-010**: On first opening the area with no filters chosen, the dashboard MUST apply a default placed-date range of the last 30 days, shown pre-set and editable in the filter controls, and MUST present the matching orders with the most recently placed first. The administrator MUST be able to widen or clear this default range. The total count MUST be labelled as the number of orders within the applied date range, not the platform-wide total.

#### Filtering the list

- **FR-011**: The dashboard MUST provide a status filter offering exactly the supported order statuses (pending, accepted, preparing, ready for pickup, assigned to driver, picked up, on the way, delivered, completed, cancelled, pending review, quoted), selectable one at a time, plus an "all statuses" option.
- **FR-012**: The dashboard MUST provide a city filter listing the platform's cities, including deactivated ones, so the administrator can restrict the list to orders whose cook is in the chosen city; a deactivated city MUST be a usable filter value.
- **FR-013**: The dashboard MUST provide a placed-date range filter with a "from" date and a "to" date, each optional; when both are set the range is inclusive, with the "to" date covering the whole day up to its final second; when only one is set the other side of the range is unbounded.
- **FR-013b**: All date handling in this feature — displaying an order's placed and requested-delivery dates and times, computing the default "last 30 days" window, and interpreting the "from" date as start-of-day and the "to" date as end-of-day (23:59:59) — MUST use the fixed Egypt local time zone (Africa/Cairo) for every administrator, regardless of the administrator's device time zone.
- **FR-013a**: The status and city filters MUST apply immediately when the administrator selects a value (each selection resets pagination to the first page and re-runs the list). The placed-date range MUST be applied only via an explicit "Apply" control — changing a date field alone MUST NOT trigger a request. A "Reset" control MUST clear the status and city filters and return the placed-date range to the default "last 30 days".
- **FR-014**: Before sending a placed-date range request, the dashboard MUST check locally that the "from" date is not later than the "to" date; if it is, the dashboard MUST block the request, show a "the start date must not be after the end date" message against the date fields, and leave the current results unchanged. If the platform still returns this error, the dashboard MUST surface it the same way without replacing the current results.
- **FR-015**: When the platform rejects a filter value — an unknown status, a non-existent city, or an unparseable date — the dashboard MUST show a clear, specific message for that case and MUST NOT treat the request as successful or update the list with results for the invalid filter.
- **FR-016**: The dashboard MUST allow status, city, and date-range filters to be combined, and MUST keep the other filters in effect when one changes. An immediate filter (status or city) MUST re-run the combined filter from the first page as soon as it changes; a placed-date range change MUST re-run the combined filter from the first page when "Apply" is used.
- **FR-017**: The dashboard MUST keep the active filters in effect across page navigation, so every retrieved page reflects the same filter set, and the total count MUST reflect the filtered set.
- **FR-018**: When valid filters match no orders, the dashboard MUST show a "no orders match these filters" state, distinct from the unfiltered empty state, with the filters still visible and adjustable, and MUST provide a way to reset the filters at once (clearing the status and city filters and returning the placed-date range to the default "last 30 days").

#### Inspecting a single order

- **FR-019**: The dashboard MUST let the administrator open the full detail of a single order from its row in the list. The detail MUST be presented as a modal dialog centred over the list, with no dedicated route for a single order; the list stays loaded behind it with its filters and scroll position preserved.
- **FR-020**: The order detail MUST show the order number, the cook, the order type, the status, the requested delivery date and time slot, and the subtotal, delivery fee, and total. It MUST also show the customer identifier and the delivery-address identifier as plain reference identifiers (numbers), clearly labelled as identifiers; it MUST NOT show a customer name or a textual delivery address (these are not available on this screen) and MUST NOT make an additional request to obtain them.
- **FR-021**: The order detail MUST list every line item of the order with its item name, unit price, quantity, and line total; when the order has no line items yet, the detail MUST show an explicit "no line items yet" rather than an unexplained empty table.
- **FR-022**: The order detail MUST show the customer's note when one is present, and MUST NOT show a placeholder as if it were content when there is none.
- **FR-023**: The order detail MUST show the cancellation reason when the order was cancelled and a reason is present, and MUST NOT show a cancellation reason otherwise.
- **FR-024**: For a custom order, the order detail MUST show the custom details — the occasion type, the guest count, the requested-dishes free text, the minimum and maximum budget, and the requested delivery date and time — showing only the values that are present without placeholders for those that are absent.
- **FR-025**: For a regular order, the order detail MUST NOT show a custom-details block.
- **FR-026**: The order detail is in scope for this phase and MUST be built entirely from the data already present in the list response — the dashboard MUST NOT make an additional per-order request to render it. The detail MUST NOT present an order status history or a price quote (these are not available on this screen) and MUST NOT show an empty timeline or empty quote as though data failed to load.
- **FR-026a**: The order detail layout MUST reserve a clearly identified place for a future status timeline and price-quote section, so a later phase can populate them from the shared order-details endpoint without redesigning the detail view. In this phase that place is simply not rendered (no empty-looking section is shown).
- **FR-027**: When the administrator closes the order detail dialog (via its close control, the Escape key, or dismissing the overlay), the dashboard MUST return them to the same page and scroll position in the list, with the active filters unchanged, and MUST restore keyboard focus to the row control that opened the dialog.

#### Cross-cutting

- **FR-028**: This is a read-only oversight screen: the dashboard MUST NOT offer any action that changes an order (no status change, no cancellation, no assignment, no editing).
- **FR-029**: Every request the dashboard makes for this feature MUST carry the administrator's active session credential, and MUST rely on the dashboard's shared session-loss handling (return to the sign-in screen) when a request is rejected as unauthenticated.
- **FR-030**: The Orders Oversight area MUST be denied to a signed-in user whose role is not administrator, consistent with the rest of the admin dashboard.
- **FR-031**: The dashboard MUST interpret the standard response envelope for this feature, using its success flag and message to drive error notifications and surfacing field-level validation messages (for example against the from-date, to-date, status, or city) where the response provides them.
- **FR-032**: For unexpected server errors on any request in this feature, the dashboard MUST show a generic "something went wrong, please try again" message and MUST keep the view in a consistent state (no stale results shown as authoritative).
- **FR-033**: The Orders Oversight area MUST reuse the dashboard's existing shell — the shared layout, sidebar navigation, API client, authentication guard, and notification infrastructure established in earlier phases — and MUST add a sidebar entry for the area.
- **FR-034**: The Orders Oversight area MUST be presented Arabic-first with a right-to-left layout, including the table, the filters, the pagination controls, the order detail, and all error, empty, and loading states. Money amounts, dates, and time slots MUST be formatted consistently with the rest of the dashboard.
- **FR-035**: The Orders Oversight area — the table, the filters, the pagination controls, the order detail, and all error, empty, and loading states — MUST meet WCAG 2.1 AA: controls and fields have programmatic labels; the flow is fully keyboard operable with a visible focus indicator; the order detail dialog traps and restores focus and is dismissible by keyboard; the table has a programmatic header association for each column; order type and status are not conveyed by colour alone; changes to the result set and total count (including the no-match state) are communicated to assistive technology; and validation and error messages (including invalid-date and start-after-end) are announced to assistive technology.
- **FR-036**: The dashboard MUST keep the applied filter state (status, city, from-date, to-date) and the current page number synchronised with the page URL's query string, so reloading the page restores the same view and the URL can be shared with another administrator. Opening the area with no query parameters MUST start from the default view (last 30 days, page 1). Applying, changing, or resetting a filter and moving between pages MUST update the URL accordingly. The open/closed state of the order detail dialog and which order it shows MUST NOT be encoded in the URL.

### Key Entities *(include if feature involves data)*

- **Order**: A single order placed on the platform. Key attributes shown here: identifier and order number; the customer identifier and delivery-address identifier (numeric references only — no name or textual address is available on this screen); the cook it belongs to (identifier, display name, avatar) and, by extension, that cook's city; the order type (regular or custom); the current status (one of the twelve order statuses); the requested delivery date and time slot; the money breakdown (subtotal, delivery fee, total); the customer's note; and, when cancelled, a cancellation reason. Read-only in this feature.
- **Order line item**: One item within an order — its identifier, the dish it refers to, the item name as ordered, the unit price, the quantity, and the line total. A regular order has one or more; a custom order may have none until it is quoted.
- **Custom order details**: The extra information attached to a custom order — the occasion type, the guest count, a free-text description of the dishes requested, a minimum and maximum budget, and a requested delivery date and time. Absent (empty) for regular orders.
- **Order status**: The stage an order is at. Twelve values: pending, accepted, preparing, ready for pickup, assigned to driver, picked up, on the way, delivered, completed, cancelled, pending review, quoted. Used as a single-select filter and shown per order; not editable here.
- **Order filter criteria**: The combination the administrator uses to narrow the list — an optional single status, an optional city (any city, active or not), and an optional placed-date range (from and/or to, the to-date inclusive to end of day) — plus the page number. The from-date must not be later than the to-date.

## Assumptions

- The backend endpoint described in `admin-dashboard-api.md` Phase 7 (`GET /admin/orders`) already exists and behaves as documented: the paginated envelope `{ items, page, per_page, total }` with `per_page` fixed at 20; the query parameters `status`, `city_id`, `placed_from`, `placed_to`, and `page`; the `placed_to` value snapped to 23:59:59; the per-order payload fields listed in the doc; `quote` always `null` and `status_history` always `[]` in list results; and the validation errors (422 for an invalid `status`, a non-existent `city_id`, an invalid date, or `placed_from` later than `placed_to`) plus the status codes 401, 403, and 500.
- This feature covers only the admin dashboard web client's behaviour for observing orders. It does not include the backend, the shared order-details endpoint, any order lifecycle actions (accepting, cancelling, assigning a driver, quoting), customer- or cook-facing order views, or reporting/aggregation (which is Phase 8).
- The administrator session, sign-in, and session-loss handling are provided by the Admin Authentication & Session feature (Phase 1) and are reused here rather than redefined. The shared layout, sidebar, API client, and notification infrastructure from earlier phases are reused, and a sidebar entry is added for this area.
- The city filter's list of cities is obtained from the cities data already available to the dashboard (the Phase 5 `GET /admin/cities` endpoint), and includes deactivated cities so they can still be used as a filter. The dashboard sends the chosen city's identifier as `city_id`.
- `city_id` filters on the cook's city, as stated in the endpoint doc; there is no separate customer-city or delivery-city filter in this feature.
- The endpoint returns only a numeric `customer_id` and `delivery_address_id` — no customer name and no textual delivery address. The dashboard shows these two identifiers in the order detail only, as labelled reference numbers, and does not resolve them to names/addresses (that would need an endpoint outside this phase's scope). The order list has no customer column.
- The status filter is single-select, matching the single `status` query parameter; there is no multi-status selection in this version.
- The status and city filters apply on selection (no per-filter "apply" step); the placed-date range is applied with an explicit "Apply" control because it needs a local from/to ordering check before a request is sent. A single "Reset" control clears status and city and restores the default 30-day range.
- Results are ordered most-recently-placed first. The backend's exact default ordering is assumed to be by placement time descending; the dashboard does not offer configurable column sorting in this version.
- `per_page` is fixed at 20 by the backend and is not configurable from the dashboard.
- On first open, the dashboard applies a default `placed_from` of 30 days before today (and no `placed_to`, so "now" is the open end), shown pre-set in the filter controls; the administrator can widen or clear it. The displayed total is the count within the applied range, and this is labelled as such rather than presented as a platform-wide total.
- The order detail is shown as a modal dialog over the list (no per-order route), consistent with the dashboard's existing dialog pattern, and is built entirely from the data already returned in the list item (line items, custom details, totals, notes, cancellation reason) with no additional per-order request; because `quote` and `status_history` are never populated here and the shared order-details endpoint is out of scope for this phase, the detail does not show a status timeline or a price quote, but its layout reserves a clearly identified place so a later phase can add them from the shared order-details endpoint without redesigning the detail.
- Auto-refresh: the dashboard re-retrieves the current view on a recurring interval only while the first results page is shown and the placed-date range is the default "last 30 days" or wider (no administrator-set narrower range). It is off on any later page and for any custom narrower range, can be turned off by the administrator, and never disturbs scroll position, filters, or an open order detail. The polling interval is a dashboard-side choice (assumed 30–60 seconds) and is not driven by the backend.
- Dates entered for the placed-date range are interpreted in fixed Egypt local time (Africa/Cairo) for every administrator; the from-date is treated as the start of that day and the to-date as the end of that day (23:59:59) in that zone, consistent with the backend snapping `placed_to` to 23:59:59. The backend is assumed to evaluate `placed_from`/`placed_to` in the same Egypt local zone; if it instead expects a different zone or an explicit offset, the dashboard converts the Cairo-local day boundaries accordingly before sending them. Order timestamps returned by the backend are displayed in the same zone.
- Money values (`subtotal`, `delivery_fee`, `total`, `unit_price`, `line_total`, `budget_min`, `budget_max`) are displayed using the dashboard's standard currency formatting; no currency conversion or rounding beyond display formatting is performed.
- The screen is read-only; there is no data mutation and no optimistic UI. A manual refresh is always available; conditional auto-refresh is described above.
- The applied filters and current page are held in the page URL's query string (shareable, survive reload); the default view (last 30 days, page 1) is what an empty query string resolves to. The order-detail dialog is transient UI state and is deliberately not represented in the URL. A shared URL whose filters/page resolve differently for the recipient (for example a page number now beyond the last page) falls back to the same empty-state and "no orders on this page" handling defined for the feature. Whether auto-refresh runs is still governed by FR-009a (first page + default-or-wider date range), evaluated from the URL-derived state.
- The area is Arabic-first and right-to-left, consistent with the dashboard's language conventions; English text within order data (for example an English dish name) is still displayed, left-to-right within its cell, but the overall layout is RTL.
- User-facing wording in this spec is descriptive, not final copy, and follows the dashboard's existing language conventions.
